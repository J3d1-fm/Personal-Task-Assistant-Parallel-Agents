Personal Task Assistant Technical Documentation

Version: 0.4.1
Last updated: 2026-06-05

Overview

Personal Task Assistant is a FastAPI application with a server-rendered HTML shell, static CSS/JS assets, and JSON API endpoints for task creation, task updates, agent queue reads, parallel agent task claims, agent work reports, context ingestion, and reminders.

Version 0.4.0 added a parallel Codex execution contract. External runners can
claim several Codex-owned backlog tasks in one request, fan them out to separate
workers, and have each worker append a structured report to its task card.

Version 0.4.1 extends that contract for the Personal Codex operating flow.
Parallel claims can also bind Codex-owned tasks that are already `in_progress`
when no active `agent_id` and `agent_run_id` are attached yet. Agent reports can
now use `needs_input` with `question_text` to block a task while returning a
clear question for the automation chat.

Runtime Behavior

Task loading still calls:

GET /api/tasks?include_done=true

Task creation still calls:

POST /api/tasks

If the request payload omits `due_at`, the store layer assigns a DD estimate before writing the task. This applies to manual UI creates, `POST /api/tasks`, `POST /api/agent/tasks`, and context-ingest-created tasks.

Task updates still call:

PATCH /api/tasks/{task_id}

The browser no longer follows each successful PATCH with a full `GET /api/tasks?include_done=true`. It updates the in-memory task list immediately, renders the changed task state, and then replaces the local task with the server response. On request failure, it restores the previous local task state.

Task dismissal calls:

DELETE /api/tasks/{task_id}

Dismiss removes the task from the local UI immediately and restores it only if DELETE fails.

Dismiss is a hard delete in the live store. When Sheets history is enabled, it also appends a `dismissed` event row using a task snapshot captured before the active task data disappears from Firestore or SQLite.

The browser UI computes these display-only concepts locally:

- Active tasks: all tasks where status is not done.
- Overdue tasks: active tasks with due_at or reminder_at earlier than the current browser time.
- Due-soon tasks: active tasks with due_at or reminder_at within the next 24 hours.
- My next actions: active tasks assigned to me.
- Codex work: active tasks assigned to codex.
- Needs review: tasks with waiting_review status.
- Unassigned: active tasks with unassigned assignee.
- Agent queue: active Codex-owned tasks in backlog or in_progress.
- Human input: active tasks assigned to me, waiting_review, or blocked.

Agent API:

GET /api/agent/queue

Returns:

- `summary`: counts for active, overdue, due_soon, codex_ready, human_input, review, blocked, and unassigned.
- `tasks`: selected tasks sorted by `smart`, `due`, `created`, `updated`, `priority`, or `owner`.

POST /api/agent/tasks

Creates one task using the normal task schema and records the history note `agent_api`.

POST /api/agent/parallel/claim

Accepts `limit`, optional `agent_ids`, `sort`, and
`claim_started_without_agent`. Selects Codex-owned backlog tasks and, by default,
Codex-owned `in_progress` tasks without `agent_id` and `agent_run_id`.
It conditionally marks them `in_progress`, stores `agent_id`,
`agent_run_id`, and `agent_claimed_at`, and returns one assignment per selected
agent. This endpoint is the handoff point for a runner that will start multiple
Codex workers in parallel. It does not execute the tasks inside the FastAPI
process.

Set `claim_started_without_agent=false` for strict backlog-only execution. The
default `true` value supports manual delegation: a user can assign a card to
Codex, move it to `In progress`, and the next runner execution can bind itself
to that card without resetting the status.

POST /api/agent/tasks/{task_id}/report

Accepts `agent_id`, `run_id`, `status`, `summary`, optional `artifact_url`,
optional `external_status`, optional `message_text`, optional `question_text`,
optional `chat_report`, and optional `next_status`.

The endpoint rejects reports unless the task is currently `assignee=codex`,
`status=in_progress`, and the payload matches the task's active `agent_id` and
`agent_run_id`. It appends a delimited structured report block to `description`.
`artifact_url` must use `http`, `https`, `mailto`, or `slack`.
Default status handling is:

- `completed`, `sent`, and `draft` -> `waiting_review`
- `needs_input`, `blocked`, and `failed` -> `blocked`
- `skipped` -> `backlog`

The response returns the updated task plus `chat_report`. If `chat_report` is not
provided, the server generates concise chat text from the task title, summary,
artifact link, external status, message text, and question text.

After a report is accepted, the active claim identity is cleared by setting
`agent_id`, `agent_run_id`, and `agent_claimed_at` to null. The structured report
block remains in `description` as the historical record. This lets a
`needs_input` task move to `Blocked`, receive a user answer, return to
`In progress`, and be claimed by a fresh agent run.

POST /api/agent/ingest/context

Alias for context ingestion so external agent clients have a consistent `/api/agent/*` surface.

Storage And Retention

Production storage:

- Cloud Run runs the FastAPI app.
- `TASK_STORE=firestore` selects the Firestore backend.
- Task records are stored in the Firestore collection `tasks`.
- The numeric task id counter is stored in Firestore at `metadata/task_counter`.
- There is no TTL, retention job, or archive job in the current code.

Local development storage:

- `TASK_STORE=sqlite` selects the SQLite backend.
- Tasks are stored in the local SQLite file configured by `DATABASE_URL`, usually `task_tracker.db`.

History behavior:

- `created_at`, `updated_at`, `completed_at`, source fields, and source context are stored on each task.
- Done tasks remain in storage indefinitely unless deleted.
- Dismiss deletes the task permanently.
- When `TASK_HISTORY_SHEET_ID` is configured, the app appends task events to Google Sheets.
- Recorded event actions are `created`, `updated`, `completed`, and `dismissed`.
- Context ingestion creates normal `created` rows with `note=context_ingest`.
- Reminder reads do not currently write history because they do not mutate a task.

Spreadsheet option:

The tracker can export history to Google Sheets, but a spreadsheet is a weaker operational database than Firestore. It is reasonable for a human-readable archive or append-only history export. It is riskier as the primary live store because concurrent writes, id generation, filtering, deletes, API latency, and auth boundaries become more fragile.

Recommended spreadsheet path if needed:

- Keep Firestore as the live task store.
- Use the append-only Google Sheets history export for created, updated, completed, and dismissed events.
- Use Sheets for review/reporting and Firestore for the live queue.

History spreadsheet configuration:

- `TASK_HISTORY_SHEET_ID` is the raw Google Spreadsheet id.
- `TASK_HISTORY_SHEET_TAB` defaults to `Task History`.
- The Cloud Run service account must have writer access to the spreadsheet.
- The Google Sheets API must be enabled in the Cloud project.
- Deployment-specific spreadsheet names, URLs, service accounts, project ids, OAuth secrets, API keys, and local credential files are intentionally excluded from the public repository.

History columns:

- `event_at`, `action`, `task_id`, `title`, `status`, `previous_status`, `assignee`, `previous_assignee`, `priority`, `previous_priority`, `origin`, `source_name`, `source_url`, `due_at`, `previous_due_at`, `reminder_at`, `completed_at`, `created_at`, `updated_at`, `description`, `source_context`, `note`.

Local Development Auth

When `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` are empty, and the app is not considered hosted, the browser UI creates a local session automatically.

The app is considered hosted when any of these are true:

- Firestore is enabled through `TASK_STORE=firestore`.
- `SESSION_COOKIE_HTTPS=true`.
- `PUBLIC_BASE_URL` starts with `https://`.

The local session email is the first configured `ALLOWED_GOOGLE_EMAILS` value, or `local-dev@task-tracker.local` if no allowlist is configured.

This fallback is intended only for local development so the UI can be inspected at `http://127.0.0.1:8000/` without creating Google OAuth credentials.

Version 0.4.0 adds three task fields: `agent_id`, `agent_run_id`, and
`agent_claimed_at`. Firestore is schemaless. SQLite runs a small startup schema
guard that adds these columns to existing local databases when missing. Agent
work reports are appended to the existing `description` text field as delimited
structured blocks.

Rollback Notes

To roll back version 0.4.1, revert these files to the previous version:

- app/agent_reports.py
- app/config.py
- app/main.py
- app/schemas.py
- app/store.py
- app/static/app.js
- app/static/styles.css
- tests/test_agent_parallel.py
- CHANGELOG.txt
- README.md
- docs/API.md
- docs/PM_GUIDE.md
- docs/TECHNICAL_DOCUMENTATION.txt

The changelog and this technical documentation can remain as history or be
reverted with the same version rollback. If rolling back only from 0.4.1 to
0.4.0, Codex-owned `in_progress` tasks without an active claim will no longer be
claimable by `/api/agent/parallel/claim`, `needs_input` and `question_text` will
not be accepted by the report endpoint, and successful reports will no longer
clear active claim identity. If rolling back to 0.3.1, parallel claim/report
endpoints and collapsible Codex work reports disappear, but the basic agent queue
remains. Existing report blocks remain plain text in descriptions unless
manually cleaned. If rolling back to 0.3.0, the installer and agent install docs
disappear but the basic agent queue/API behavior remains. If rolling back to
0.2.6, agent queue endpoints and automatic DD estimates disappear. If rolling
back past 0.2.4, also unset `TASK_HISTORY_SHEET_ID` on Cloud Run.
